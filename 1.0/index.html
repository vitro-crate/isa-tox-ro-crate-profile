Overview

This profile extends the ISA RO-Crate profile (ISA RO-Crate Profile, originally produced by NFDI4Plants) with the entity types needed to describe experimental in vitro toxicology studies and New Approach Methodologies (NAMs).

It is the domain layer of a three-layer architecture: the base RO-Crate layer provides a portable, self-describing data package on Schema.org; the ISA RO-Crate Profile provides the structural Investigation → Study → Assay hierarchy with experimental steps modelled as Bioschemas LabProcess / LabProtocol; and this profile adds the toxicology-specific, ontology-backed requirements on top.

The extension is additive and reuse-first: each concept is expressed through the most specific applicable Schema.org or Bioschemas type, refined where necessary by an existing ontology term: a step by the protocol type of the record it executes, a test-system source by its sampleType. Test/control chemicals are bioschemas.org/MolecularEntity instances; the test system is a Sample carrying sampleType — a cell line, primary cells, an organoid or other 3D model, a tissue or organ fragment, a sub-cellular fraction — of which cell lines and primary cells carry requirements of their own here; and the experimental workflow is a chain of LabProcess steps discriminated as TestSystemPreparation, Exposure, EndpointReadout, and DataAnalysis.

Requirement levels use RFC 2119 keywords, as recommended by the RO-Crate 1.2 profile conventions: MUST (required for conformance), SHOULD (recommended; absence is reported as a warning), and MAY (optional). The shapes are open-world: a property this profile does not name is neither checked nor forbidden (no shape declares sh:closed), so a crate may carry further metadata without affecting conformance. The figure below is the model of an in vitro NAM study in terms of this profile's entity types: box colour gives the type, line style the relationship. Each material is a Bioschemas Sample, each step a LabProcess following a LabProtocol, and the chemicals a MolecularEntity.

How the reference builder encodes this. The tables below give the canonical property names and expected types (what the SHACL shapes check). The vitro-crate builder emits them through compact JSON-LD aliases defined in the crate's @context, all RDF-identical to the canonical predicates:

  • @type is the bare token (Sample, LabProcess, LabProtocol, PropertyValue, …); the @context expands it to the Bioschemas/schema.org IRI named in the tables.
  • process parameters appear under parameter (→ schema:additionalProperty), inputs under input (→ schema:object), outputs under output (→ schema:result), and derivesFrom expands to schema:isBasedOn.
  • the AOP links are written as aop on a Study and keyEvent on an Assay, both expanding to schema:mentions, and a compound's hashed structure as inchikey (→ schema:inChIKey).
  • each parameter is a PropertyValue node with a deterministic @id, a propertyID IRI and optional unitText — never an inline literal (the LabProcess shapes use sh:class schema:PropertyValue).
  • a derived Sample's derivesFrom links the Sample it was made from; only cultured material is constrained: at most one parent Sample, or two or more for a co-culture.

The four LabProcess shapes are selected by the intendedUse of the protocol record a step executes: a term of the test system preparation types set, treatment protocol EFO:0003969, assay protocol BAO:0000523, data transformation OBI:0200000. A LabProcess whose record carries none of these is targeted by no tox shape and is checked only by the base + ISA layers, and a type outside the list is a warning.

Conformance

A crate following this profile declares conformance using the RO-Crate 1.2 convention: the RO-Crate Metadata Descriptor's conformsTo carries only the single base-specification URI, while the profile URIs the crate targets are declared on the Root Data Entity (./). Each referenced profile is also declared as a Profile contextual entity.

{
  "@id": "ro-crate-metadata.json",
  "@type": "CreativeWork",
  "conformsTo": {"@id": "https://w3id.org/ro/crate/1.2"},
  "about": {"@id": "./"}
}

The Root Data Entity declares the targeted profiles:

{
  "@id": "./",
  "@type": "Dataset",
  "conformsTo": [
    {"@id": "https://github.com/nfdi4plants/isa-ro-crate-profile"},
    {"@id": "https://w3id.org/ro/crate/isa-tox/1.0"}
  ]
}

The ISA layer is declared with the IRI the profile actually extends (see profiles/shapes/tox/profile.ttl, prof:isProfileOf); a stable w3id.org/ro/crate/isa/… permalink is not yet registered. The referenced profiles are declared as contextual entities:

{
  "@id": "https://github.com/nfdi4plants/isa-ro-crate-profile",
  "@type": ["CreativeWork", "Profile"],
  "name": "ISA RO-Crate Profile"
},
{
  "@id": "https://w3id.org/ro/crate/isa-tox/1.0",
  "@type": ["CreativeWork", "Profile"],
  "name": "ISA-Tox RO-Crate Profile",
  "version": "0.1.0-draft.1"
}

Note — RO-Crate 1.2 placement. RO-Crate 1.2 recommends declaring the profiles a crate targets on the Root Data Entity (./) and reserving the Metadata Descriptor's conformsTo for a single base-specification value — which this profile follows.

A machine-readable Profile Crate bundling this description with the SHACL shapes MAY additionally be published at the profile URI; this is planned but not yet provided.

Requirements

A crate MUST include at least one Exposure that one of its Studies or Assays is about: it is not in vitro toxicology if nothing is exposed to a chemical. The check targets the Root Data Entity, so it holds even for a crate that contains nothing else. Each Exposure's protocol then names its compounds (see LabProcess - Exposure).

Study - Adverse Outcome Pathway

Is based on the ISA Study. A study addresses one Adverse Outcome Pathway, referenced via schema:mentions at the Study level; each of its assays annotates the one Key Event it measures (Assay - Key Event). The referenced node is the AOP-Wiki entity itself: @id is its identifiers.org IRI as used in AOP-Wiki RDF (https://identifiers.org/aop/<id>), typed AdverseOutcomePathway (AOPO, the ontology AOP-Wiki RDF itself uses) and DefinedTerm, with AOP-Wiki as its term set and the wiki page as url. A crate MAY carry the surrounding AOP-Wiki subgraph — Key Events (https://identifiers.org/aop.events/<id>) and their KeyEventRelationship nodes (https://identifiers.org/aop.relationships/<id>), cross-linked by upstream_event / downstream_event — so the pathway reads without a network call.

The adverse outcome the study is ultimately about is reached through the pathway, via its has_adverse_outcome, rather than named again on the Study: an adverse outcome occurs in more than one pathway, so the pathway is the more specific statement and the one the assays' Key Events are steps of.

Assay - Key Event

Is based on the ISA Assay. An assay measures one endpoint, annotated with the AOP-Wiki Key Event it reads out via schema:mentions — the level below the Study's AOP, so a reader can tell which step of the pathway each assay covers. The referenced node is the AOP-Wiki Key Event itself: @id is its identifiers.org IRI as used in AOP-Wiki RDF (https://identifiers.org/aop.events/<id>), typed KeyEvent (AOPO) and DefinedTerm, with the wiki page as url.

What the assay measures is named in BAO terms, the vocabulary this profile uses throughout for assay description: at this level through measurementMethod and measurementTechnique, and in more detail on the step that reads the endpoint, whose parameters carry the detection instrument, measured entity and endpoint as BAO terms (see LabProcess - Endpoint Readout).

MolecularEntity - Test and Control Chemicals

The test and control chemicals are modelled as bioschemas.org/MolecularEntity instances. A MolecularEntity is one defined molecule, and it is the type that carries the structure and identity properties this profile asks for — inChIKey, smiles, inChI, molecularFormula — so a reader can tell which compound was tested and look it up in PubChem or CompTox. Schema.org's broader ChemicalSubstance covers a portion of matter of constant composition — a mixture or preparation as readily as a pure compound — and defines no structure property at all, so a compound typed that way cannot be matched by structure. A test item that is genuinely a mixture has no modelling in this version. Concentration is not a property of the compound — it is carried per well by the Exposure's condition table (CSVW), so there is no per-concentration chemical Sample.

Property Required Expected Type Description
@id MUST Text or URL SHOULD be an absolute, resolvable compound IRI — a PubChem, CompTox or CompoundWiki entry. A crate-local identifier (#iopanoic-acid) is allowed, and is the only option for a coded or proprietary test item with no public record; the compound's identity is carried by inChIKey and identifier either way.
@type MUST bioschemas.org/MolecularEntity —
name MUST Text The compound name.
identifier SHOULD Text, URL or schema.org/PropertyValue A compound identifier (e.g. InChIKey, CAS, PubChem CID), ideally a PropertyValue carrying its scheme, resolving to an authoritative resource.
inChIKey SHOULD Text The hashed InChI for unambiguous structure lookup.
smiles SHOULD Text The compound structure as SMILES.
inChI MAY Text The compound structure as InChI.
molecularFormula MAY Text The molecular formula.
url MAY URL Link to an external record, e.g. PubChem, ChEBI or CompoundWiki.

Sample - Source Cells

Is based on the Bioschemas bioschemas.org/Sample type (ISA Sample). The cells or material a Test System Preparation starts from — the test system in the sense IUCLID OHT 201 gives it. One Sample carries a categorical annotation via sampleType (a DefinedTerm) saying which kind it is: a cell line, primary cells, an organoid or other 3D model, a tissue or organ fragment, a sub-cellular fraction, a whole organism. Cell lines and primary cells add requirements of their own below; any other kind is described by this section alone, under its own term. A Sample a preparation consumes is source cells whatever it states, so one with no sampleType is still reported. The labels "CellLine" / "PrimaryCell" older crates carry in additionalType are aliases.

A test system is dual-typed Sample and BioSample, which is a Bioschemas subtype of Sample: the inherited ISA requirements and every shape here keep matching on Sample, while a BioSample-aware consumer recognises the material and can read cellType, anatomicalStructure and sex directly. Those three are BioSample's own properties, pending integration into Schema.org. They state the same facts this profile also carries as Characteristic PropertyValue items with their ontology terms, and it is the Characteristic that the shapes check — so a crate stays conformant whether or not it carries the BioSample properties as well.

Property Required Expected Type Description
@id MUST Text or URL Could be the unique sample name.
@type MUST BioSample, a Bioschemas subtype of bioschemas.org/Sample The array ["BioSample", "Sample"], most specific first. Sample MUST stay in it: every requirement here is matched on that type.
sampleType MUST schema.org/DefinedTerm A categorical annotation of the material as a fixed, resolvable ontology term; see the expected terms below.
cellType MAY Text, URL or schema.org/DefinedTerm BioSample: the cell line, lineage or biological classification of a cell. Also carried as a cell-type Characteristic (EFO:0000324), which is what the shapes check.
anatomicalStructure MAY schema.org/AnatomicalStructure, DefinedTerm or URL BioSample: the organ or tissue the material was collected from. Also carried as Organ / Tissue Characteristics (UBERON:0000062, UBERON:0000479).
name MUST Text A name identifying the sample, e.g. the cell-line name.
additionalProperty SHOULD schema.org/PropertyValue (Characteristic) Characteristics of the sample, e.g. passage number or growth conditions.

Sample - Exposed Test System

The material an Exposure produces: the test system after the chemical was applied. It carries the same requirements as the Test System it derives from — same type, same sampleType "cell culture", isBasedOn the test system it was exposed from — so it has no table of its own. What makes it the exposed material is stated on the step, not on the Sample: an Exposure MUST have the test system as schema:object and the exposed material as schema:result. Following isBasedOn back from it therefore walks the whole chain: exposed test system → test system → source cells.

LabProcess - Exposure

Is based on the Bioschemas DRAFT bioschemas.org/LabProcess type (ISA LabProcess), typed by its protocol record's intendedUse, treatment protocol (EFO:0003969), to represent exposing the cell-based test system to the chemical(s). It takes the cultured cell Sample as its object, executes a protocol record naming the compounds it applied, and emits the exposed cell Sample(s) as its result. The experimental design is a run-specific condition table (CSVW): a data file about those exposed Samples, in which each row records a single well (cell line, compound, concentration, exposure duration).

Where the compound goes. The MolecularEntity compound is not a process object: the inherited ISA LabProcess shape restricts schema:object (and schema:result) to File/Sample/BioSample, so a MolecularEntity there fails validation. The compound is a reagent of the Exposure's protocol record, which MUST name at least one. The procedural SOPs name no compound and are what the record isBasedOn, so the assay stays executable with other chemicals: a re-run needs a new record and condition table and the same SOPs.

Property Required Expected Type Description
@id MUST Text or URL Could identify the process using the process name and protocol reference.
@type MUST bioschemas.org/LabProcess —
name MUST Text The name of the process, e.g. "Exposure".
object MUST bioschemas.org/Sample or File The input cell sample(s) being exposed. At least one. (A MolecularEntity is not allowed here — see note above.)
parameterValue MUST schema.org/PropertyValue (Parameter) Exposure parameter(s); see expected values below. At least one.
result MUST bioschemas.org/Sample or File The exposed sample(s) the step produces. At least one. The condition table is not a result: it is a File + csvw:Table about the exposed Samples, and each exposure SHOULD have one.
executesLabProtocol MUST bioschemas.org/LabProtocol The step's protocol record: exactly one (SHOULD), whose reagents MUST include at least one test or control compound (a MolecularEntity).

LabProtocol - Protocol record

Is based on the Bioschemas bioschemas.org/LabProtocol type (ISA LabProtocol). Each LabProcess above executes exactly one: a record of the protocol its step follows, present whether or not the lab deposited a document for it, because its intendedUse says what kind of step it is. A deposited SOP or script stays a File co-typed LabProtocol (the RO-Crate 1.2 multi-type idiom) and is what the record is isBasedOn, so one document can serve several steps, each record carrying its own type. ISA-JSON has no isBasedOn on a protocol, so that link is lost on conversion to ISA-JSON.

Property Required Expected Type Description
@id MUST Text or URL One record per step, e.g. the process @id followed by _protocol.
@type MUST bioschemas.org/LabProtocol —
intendedUse SHOULD schema.org/DefinedTerm The protocol type of its step, from the table below, written as {"@id": …} and described once in the graph.
name SHOULD Text The name of the protocol, e.g. "Exposure protocol".
description SHOULD Text What the lab stated about the procedure; a builder writes none of its own.
url MAY URL Where the lab published the procedure, when it stated one.
reagent MAY bioschemas.org/MolecularEntity The compounds the protocol applied. On the Exposure's record this is a MUST: the test and control compounds, at least one, checked on the Exposure step.
isBasedOn MAY File The deposited documents the step follows.
Step intendedUse
Test System Preparation a term of the test system preparation types set
Exposure EFO:0003969 treatment protocol
Endpoint Readout BAO:0000523 assay protocol
Data Analysis OBI:0200000 data transformation: no protocol-type term exists, so the OBI process class stands in, as ISA's reference dataset BII-I-1 does for extraction

Example ro-crate-metadata.json

A conforming crate types every step by its protocol record's intendedUse and every test-system source by its sampleType, as described above, and validates in three passes (base RO-Crate 1.2 → ISA → ISA-Tox).
